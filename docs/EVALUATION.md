# Evaluation report

All numbers in this document are produced by real commands:

```bash
cd backend
python -m app.evaluate                  # current dataset vs its labels
python -m app.evaluate --full           # dataset + held-out + negative control
python -m app.evaluate --holdout        # held-out set only
python -m app.evaluate --negative       # negative control only
```

Results are written to `data/evaluation_results.json`. Thresholds were **not**
tuned on the held-out or negative-control sets; the detection tolerances
(₹1.00 money, 7 days, 94% identity, 55% match) predate the held-out generator
and come from the original design.

## 2. Held-out synthetic set (harsher corruptions, different seed)

Generated by `app.eval_data.generate_eval(1000, seed=90210, per_type=20)` —
deliberately unlike the demo generator: reference IDs carry typos (swaps,
deletions, case flips), split invoices post only 50% of taxable value, amount
alterations use awkward magnitudes (+450.01, +999.99, ×1.05–1.12), tax
alterations +8–15% or flat ₹15.75–₹250, date drift 8–20 days, GST slab 0%
included.

| discrepancy_type | TP | FP | FN | Precision | Recall | F1 |
|---|---|---|---|---|---|---|
| amount_mismatch | 17 | 0 | 3 | 1.0 | 0.85 | 0.919 |
| date_mismatch | 20 | 0 | 0 | 1.0 | 1.0 | 1.0 |
| duplicate_invoice | 20 | 3 | 0 | 0.870 | 1.0 | 0.930 |
| missing_gst | 20 | 0 | 0 | 1.0 | 1.0 | 1.0 |
| missing_ledger | 20 | 3 | 0 | 0.870 | 1.0 | 0.930 |
| tax_mismatch | 18 | 0 | 2 | 1.0 | 0.9 | 0.947 |

**Macro F1 = 0.9545.**

Known failure modes behind the remaining errors:

- *3 FPs on missing_ledger / duplicate_invoice*: cross-contamination between
  injected cases (e.g. an amount-mismatch row's ledger was altered, then that
  vendor also got a duplicate), plus the ₹1-tolerance contextual fallback
  matching altered rows to their originals.
- *3 FN on amount_mismatch*: the contextual fallback matched typo'd
  references with identical tax but altered taxable, masking the mismatch.
- *2 FN on tax_mismatch*: flat alterations ≤ ₹1.00 stay inside the tolerance.

## 6. Feedback loop

Stage A (Bayesian-smoothed priors, α=5, ±8-point cap) activates from the first
review; stage B (xgboost P(confirmed)) activates at 50 labelled decisions with
both classes present, with stratified-CV AUC/log-loss/Brier logged in
`models/feedback_ranker_meta.json`. With fewer than 50 labelled cases the
stage-B model is correctly *not* trained. Ranking lift is observable per case
via `ranking_explanation` (base score → feedback adjustment → ML boost) and
aggregates via `GET /api/feedback`.

## 7. Limitations

- The held-out set is still synthetic; real ERP exports will have messier
  column semantics (handled by the alias layer) but also structural cases
  (credit notes, multi-line invoices) not modelled here.
- Demo/held-out ground truth covers injected discrepancies only; organic
  errors in real data have no labels until reviewers confirm/reject.
- ML-anomaly precision is measured against injections, which are exactly the
  kind of point anomalies Isolation Forest should find; on clean data its
  flags are unverified signals by definition.
- Perfect 1.0 on the demo set reflects generator/engine symmetry and should
  be read together with the harsher held-out numbers.
- Duplicate-invoice evaluation counts a cluster as detected if any member was
  flagged; the UI shows one case per cluster.
